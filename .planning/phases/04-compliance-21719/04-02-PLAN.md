**1. findLeadsByEmail** — internalQuery:
```typescript
export const findLeadsByEmail = internalQuery({
  args: { email: v.string() },
  handler: async (ctx, { email }) => {
    return await ctx.db
      .query("leads")
      .withIndex("by_email", (q) => q.eq("email", email))
      .collect();
  },
});
```

**2. checkBlacklist** — internalQuery:
```typescript
export const checkBlacklist = internalQuery({
  args: { email: v.string() },
  handler: async (ctx, { email }) => {
    const entry = await ctx.db
      .query("optOutBlacklist")
      .withIndex("by_email", (q) => q.eq("email", email))
      .first();
    return entry !== null;
  },
});
```

**3. softDeleteLead** — internalMutation:
Patches a single lead by ID: anonymizes PII fields (contacto -> "[ELIMINADO]", email -> `anon-${leadId}@eliminated.local`, telefono -> undefined, linkedinUrl -> undefined), sets complianceStatus to "opt_out", optOutAt to Date.now(), softDeletedAt to Date.now(), hardDeleteScheduledAt to Date.now() + 30*24*60*60*1000, estado to "cerrado", subestado to "descartado", and appends audit trail entry with accion "Opt-out procesado — datos anonimizados", usuarioId "system", usuarioNombre "Compliance Bot".

**4. addToBlacklist** — internalMutation:
Args: email (string), emailHash (string), source (string — cast to the union type), motivo (optional string).
First checks if already blacklisted via `by_email` index. If exists, returns existing._id. Otherwise inserts into optOutBlacklist with optOutAt: Date.now(), tenantsNotified: [].

**5. executeGlobalOptOut** — internalMutation:
This is the orchestrator. Args: email (string), motivo (optional string).
Steps:
1. Generate emailHash: use a simple approach — since we cannot use Node crypto in Convex mutations (they run in V8), store the email itself as emailHash (in production this would be hashed, but Convex V8 runtime does not have crypto.subtle available in mutations). Add comment noting this.
2. Call addToBlacklist (but since we are in a mutation, we cannot call other mutations directly — instead inline the blacklist logic: query optOutBlacklist by email, if not found insert)
3. Query all leads with this email using by_email index
4. For each lead found: apply the same anonymization as softDeleteLead (inline the patch logic)
5. Return { blacklisted: true, leadsAffected: count }

Import `v` from "convex/values" and `internalMutation, internalQuery` from "./_generated/server". Add file header comment explaining this module handles opt-out/blacklist for Ley 21.719 compliance.

Create `convex/compliance.ts` with mutations for ARCO-POL request management and an action for sending verification emails.

Import `v` from "convex/values", `internalMutation, internalQuery` from "./_generated/server", and `internalAction` from "./_generated/server".

**1. createArcoRequest** — internalMutation:
Args: email (string), nombre (optional string), tipoSolicitud (union matching schema), detalles (optional string).
Steps:
1. Generate verificationToken using `crypto.randomUUID()` (available in Convex runtime)
2. Calculate fechaLimite: Date.now() + (15 * 24 * 60 * 60 * 1000) — 15 business days approximated as 15 calendar days for MVP
3. Insert into arcoRequests table with estado: "verificando", createdAt: Date.now()
4. Return { requestId: insertedId, token: verificationToken }

**2. verifyArcoRequest** — internalMutation:
Args: token (string).
Steps:
1. Query arcoRequests with by_token index for the token
2. If not found, return { verified: false, error: "Token invalido" }
3. If found and estado !== "verificando", return { verified: false, error: "Solicitud ya procesada" }
4. Patch: estado -> "verificada", verifiedAt -> Date.now()
5. Find all leads with this email (query leads by_email index), collect their orgIds into tenantsAfectados array
6. Patch tenantsAfectados on the request
7. Return { verified: true, requestId: request._id, tipo: request.tipoSolicitud }

**3. updateArcoStatus** — internalMutation:
Args: requestId (id of arcoRequests), nuevoEstado (union matching schema estado), respuesta (optional string).
Steps:
1. Get request by ID
2. If not found, throw Error("Solicitud no encontrada")
3. Patch with new estado, respuesta if provided, completadaAt if estado is "completada" or "rechazada"
4. Return { success: true }

**4. getArcoRequestsByEstado** — internalQuery:
Args: estado (union matching schema).
Returns all arcoRequests with that estado, ordered desc.

**5. sendVerificationEmail** — internalAction:
Args: email (string), token (string), tipo (string — "opt-out" or "arco").
Steps:
1. Determine confirmUrl based on tipo:
   - If "opt-out": `${process.env.CONVEX_SITE_URL}/opt-out/confirm?token=${token}`
   - If "arco": `${process.env.CONVEX_SITE_URL}/derechos/confirm?token=${token}`
2. Determine subject:
   - If "opt-out": "Confirma tu solicitud de baja - Sisteco"
   - If "arco": "Confirma tu solicitud de derechos - Sisteco"
3. Build HTML body with confirmation link and 24-hour expiry note. Sender: "Sisteco Privacidad <contacto@sisteco.cl>" (use existing verified sender).
4. Send via Resend API: fetch("https://api.resend.com/emails", { method: "POST", headers: { "Content-Type": "application/json", "Authorization": `Bearer ${process.env.RESEND_API_KEY}` }, body: JSON.stringify({ from, to: [email], subject, html }) })
5. Return { sent: true }

Create `convex/http.ts` with a Convex HTTP router exposing public endpoints for compliance. These endpoints are UNAUTHENTICATED — leads are not Sisteco users.

Import: `httpRouter` from "convex/server", `httpAction` from "./_generated/server", `internal` from "./_generated/api".

Create router: `const http = httpRouter();`

CORS helper: Create a function `corsHeaders()` that returns `{ "Access-Control-Allow-Origin": "*", "Access-Control-Allow-Methods": "GET, POST, OPTIONS", "Access-Control-Allow-Headers": "Content-Type" }`. Add OPTIONS handler for preflight on routes that need it.

**Route 1: GET /opt-out** — Returns HTML form page.
The HTML should be a complete standalone page with Sisteco branding (#F8F7F5 background, #111111 text, #c5ed36 accent). The form has:
- Heading: "Solicitud de Baja — Sisteco"
- Subtext: "Si no deseas recibir comunicaciones de nuestra parte, ingresa tu email para iniciar el proceso de eliminacion."
- Input field: email (type email, required, placeholder "tu@email.com")
- Submit button: "Solicitar baja" (lime accent background)
- Footer: "Sisteco — Plataforma B2B | contacto@sisteco.cl"
Return as Response with Content-Type text/html charset=utf-8.

**Route 2: POST /opt-out** — Processes opt-out submission.
1. Parse JSON body: `{ email }`
2. Validate email exists and is not empty
3. Call `ctx.runMutation(internal.compliance.createArcoRequest, { email, tipoSolicitud: "supresion" })` to create the request
4. Get back the token
5. Call `ctx.runAction(internal.compliance.sendVerificationEmail, { email, token, tipo: "opt-out" })` to send verification
6. Return JSON `{ ok: true, message: "Revisa tu email para confirmar la solicitud" }` with status 200

**Route 3: GET /opt-out/confirm** — Confirms opt-out from email link.
1. Parse token from URL query params
2. Call `ctx.runMutation(internal.compliance.verifyArcoRequest, { token })`
3. If verified and tipo is "supresion": call `ctx.runMutation(internal.optOut.executeGlobalOptOut, { email: request.email })`
4. Return HTML confirmation page: "Tu solicitud ha sido procesada. Tus datos seran eliminados de nuestro sistema."
5. If token invalid: return HTML error page: "Token invalido o expirado."

**Route 4: POST /unsubscribe** — One-click unsubscribe (RFC 8058).
1. Parse body (may be form-encoded: `List-Unsubscribe=One-Click` or JSON)
2. Extract email from URL query param `?email=...`
3. Call `ctx.runMutation(internal.optOut.executeGlobalOptOut, { email })`
4. Return Response status 200 (empty body — RFC 8058 spec)

**Route 5: POST /derechos** — ARCO-POL request submission.
1. Parse JSON body: `{ email, nombre, tipo, detalles }`
2. Validate: email required, tipo must be one of acceso/rectificacion/supresion/oposicion/portabilidad/limitacion
3. Call `ctx.runMutation(internal.compliance.createArcoRequest, { email, nombre, tipoSolicitud: tipo, detalles })`
4. Call `ctx.runAction(internal.compliance.sendVerificationEmail, { email, token, tipo: "arco" })`
5. Return JSON `{ ok: true, message: "Solicitud recibida. Revisa tu email para verificar." }`

**Route 6: GET /privacidad** — Returns privacy policy as HTML.
Read the content from `docs/legal/politica-privacidad.md` — since we cannot read files from disk in Convex HTTP actions, embed the key privacy policy content inline as an HTML page. Use Sisteco branding. Include link to `/derechos` for exercising rights and link to `/opt-out` for opting out.

**Route 7: OPTIONS preflight** for /opt-out, /derechos, /unsubscribe — return 204 with CORS headers.

Export: `export default http;`

NOTE: The verifyArcoRequest mutation returns the request data. For the opt-out confirm flow, we need the email to pass to executeGlobalOptOut. Since verifyArcoRequest already has the email in the arcoRequests table, update the flow: verifyArcoRequest should return the email in its response. If the compliance.ts from Task 2 doesn't return email, the HTTP handler should query it separately. Handle this by having verifyArcoRequest return `{ verified, email, tipo }`.

IMPORTANT: Since Convex HTTP actions cannot directly chain runMutation results into other runMutation calls within the same httpAction without using an intermediate variable, structure the code to await each call sequentially.
